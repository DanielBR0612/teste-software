### 4.2. CDU013 - Gestão de Formulários

Este documento especifica os testes que devem ser realizados para o caso de uso 013 - Gestão de Formulários, com foco específico no envio de formulários para os alunos alvo. Ele contém as informações necessárias para a construção dos scripts de teste, como preparação do ambiente, dados de entrada e resultados esperados.

#### Especificação do CDU
- **Ator principal:** Assistente Social
- **Resumo:** O usuário pode enviar um formulário criado para um público-alvo específico (todos os alunos, alunos de um auxílio específico ou alunos selecionados individualmente).
- **Pré-condição:**
    - Ter feito o login no sistema com as devidas permissões.
    - O formulário já deve estar cadastrado.
- **Pós-condição:**
    - O formulário passa do status de "rascunho" para "aberto".
    - Respostas vazias (`RespostaFormulario`) são criadas para cada aluno alvo.
    - Notificações são criadas e vinculadas aos alunos.
    - A quantidade de `alunos_solicitados` é atualizada.

#### Classes de equivalência

- **Status do Formulário:** `rascunho`, `aberto`, `concluido`
- **Data Fim:** `data_fim >= hoje`, `data_fim < hoje`
- **Modo de Envio (`solicitados`):** `todos`, `auxilio`, `individual`, `valor_invalido`
- **Disponibilidade de Alunos:** `alunos_finais > 0`, `alunos_finais == 0`
- **Validação de Modo:**
    - Auxílio: `auxilio_alvo is not None`, `auxilio_alvo is None`
    - Individual: `alunos_selecionados.exists()`, `not alunos_selecionados.exists()`

#### Análise de Valor Limite

Focada principalmente na lista de alunos gerada e na validação da data final do formulário.

#### 1) `data_fim` em relação à data atual (`hoje`)

| Caso                    | Entrada                           | Resultado Esperado                            |
| ----------------------- | --------------------------------- | --------------------------------------------- |
| Ontem (inválido limite) | `data_fim = hoje - 1 dia`         | HTTP 400, "data de término no passado"        |
| Hoje (válido menor)     | `data_fim = hoje`                 | Processamento continua (sucesso se dados OK)  |
| Amanhã (válido normal)  | `data_fim = hoje + 1 dia`         | Processamento continua (sucesso se dados OK)  |

#### 2) `alunos_finais` (quantidade de alunos retornados)

| Caso                           | Entrada                               | Resultado Esperado                                                             |
| ------------------------------ | ------------------------------------- | ------------------------------------------------------------------------------ |
| Nenhum aluno (inválido limite) | total de `alunos_query` = 0           | HTTP 404, "Nenhum aluno encontrado"                                            |
| 1 aluno (válido menor)         | total de `alunos_query` = 1           | HTTP 200, envio realizado para 1 aluno, 1 resposta criada e 1 notificação      |
| Múltiplos alunos               | total de `alunos_query` = N (N > 1)   | HTTP 200, envio realizado para N alunos, N respostas criadas e N notificações  |

#### Regras de Negócio e de Fluxo no Envio ("envio")

- **Validação de Status e Data:** O sistema inicialmente bloqueia envios caso o formulário esteja `concluido` ou a `data_fim` já tenha passado.
- **Filtro de Público (Modo de Envio):**
  - **`todos`:** Seleciona a totalidade de instâncias no modelo `Aluno`.
  - **`auxilio`:** Seleciona apenas alunos que possuem o `beneficio` vinculado ao `auxilio_alvo`. Exige que `formulario.auxilio_alvo` seja não nulo.
  - **`individual`:** Seleciona apenas alunos presentes na relação ManyToMany `formulario.alunos_selecionados`. Exige que haja ao menos um aluno na relação.
- **Processamento da Transação (`transaction.atomic`):**
  - O campo `alunos_solicitados` é atualizado para a contagem exata da lista final de alunos atingidos.
  - Se o `status` atual for `'rascunho'`, ele é automaticamente promovido a `'aberto'`. Os campos `alunos_solicitados` e `status` são salvos no banco de dados.
  - Para cada aluno filtrado, cria-se uma instância de `RespostaFormulario` vinculando formulário e aluno, definindo `completo=False` por padrão, apenas se uma resposta idêntica não existir (garantindo idempotência/evitando duplicidades). O banco os insere via `bulk_create`.
  - Gera-se uma nova `Notificacao` genérica cujo texto usa o `titulo` e a `data_fim` do formulário, e seu campo M2M `.usuario` é alimentado com todos os usuários correspondentes à lista de alunos.
- **Transação:** O código que salva respostas e cria notificações roda num bloco `with transaction.atomic()`, revertendo todas as mudanças (sem envios pela metade) se qualquer erro de banco ou de negócio ocorrer no meio da execução.

#### Regras de Negócio e de Fluxo na Submissão
- **Injeção Silenciosa e Validação (`validate_formulario_id`)**: A serialização cruza o `Formulario` enviado exigindo sua real presença na base e também impede que usuários sem o objeto `Aluno` associado na sessão atual realizem a transação.
- **Transação e Tolerâncias Múltiplas (`get_or_create`)**: Todo o processo flui em um bloco `transaction.atomic()`. Logo, se houver falha de escrita das `RespostaQuestao`, o estado do `RespostaFormulario` reverte sem ser atualizado. Para permitir refações/atualizações parciais, o sistema opta por localizar um registro existente em vez de duplicar.
- **Substituição de Respostas Destrutivas**: Quando detectada revisão, a base ativa o `.delete()` sobre todos os nós da FK reversa `RespostaQuestao.objects.filter(...)` e reconstroi novamente a partir da submissão exata.
